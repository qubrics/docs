SDK packages track the public Qubrics API contracts. A package update can be limited to one language or one surface when the change only affects that package.

## Versioning model

- SDK packages can use different major versions. The Rust crate is pre-1.0 on `0.x` and can introduce breaking changes between minor versions.
- Patch versions can differ between packages.
- Generated clients are built from the same public API contracts used by the API reference.
- API contract changes update the relevant SDK output in the same package release.
- Pin the major version your application is tested against. Review package release notes before upgrading.

## Package names and imports

Keep the package version and import path together. Installing an old-name distribution from this table installs its replacement as a dependency. It provides no old import path. Change your imports alongside your installation command, and keep the dependency lockfile your application was tested with so you can restore that version set if needed.

Use the language guides for client examples. Each release covers one package. Check the version and namespace for every language, umbrella package or related developer tool you use.

## Compatibility checks

Check the package registry for the version you install, then compare the package surface with the API reference:

- Use the [Sending API](/sending-api/introduction) for outbound email behaviour.
- Use the [Mailbox API](/mailbox-api/introduction) for mailbox and message behaviour.
- Use the [Management API](/api/introduction) for team-level resources.
- Use [API keys](/account/api-keys) to confirm the key scope before testing.

## Support requests

For SDK help, include:

- Package name and version.
- Language runtime and operating system.
- Command, import path, or client method involved.
- The API surface: Sending, Mailbox, or Management.
- Sanitised request or response details.
- `X-Request-Id` or `meta.request_id` from an API response, if present.

Do not include API keys, passwords, tokens, webhook secrets, customer data, or private account details.

## Security reports

Report suspected vulnerabilities privately through [security@qubrics.com](mailto:security@qubrics.com). Do not open a public GitHub issue for security reports.
